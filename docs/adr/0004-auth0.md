# ADR 0004 — Auth0 for identity

- **Status**: Accepted
- **Date**: 2026-05-13

## Context

B2B compliance requires MFA, anomaly detection, lockout policies, audit log of auth events, password rotation, and reliable SSO support. Rolling our own is a multi-month engineering effort plus an ongoing security surface.

## Decision

Use **Auth0** as the IdP:

- Browser uses the Auth0 Next.js SDK (server-side session cookie + access token).
- API verifies RS256 JWTs via Auth0's JWKS endpoint with key caching.
- A post-login Auth0 **Action** writes our internal `userId`, `roles`, and `permissions` as custom claims into the access token.
- MFA is required for `BUYER`, `SALES_MANAGER`, `ADMIN`, and `SUPER_ADMIN` roles.

## Consequences

- ✅ MFA, brute-force lockout, anomaly detection, and breached-password protection out of the box.
- ✅ Audit logs of every login/logout/MFA event available via Auth0's log streaming.
- ✅ We do not store passwords. Reduced PCI/SOC scope.
- ⚠️ Vendor lock-in and per-MAU pricing. Mitigated by:
  - Keeping our domain model (`User`, `roles`, `permissions`) independent of Auth0 — `auth0Id` is the only cross-reference.
  - We can migrate to Cognito / Clerk / WorkOS by swapping the verifier + login flows; downstream code is unaware.

## Alternatives considered

- **Clerk**: great DX, similar features; Auth0 wins on enterprise SSO / SAML connectors used by hospital chains.
- **NextAuth (Auth.js)** self-hosted: cheapest, but adds operational burden (TOTP, password reset, anomaly detection).
- **Cognito**: powerful but rougher DX and worse audit UX.
